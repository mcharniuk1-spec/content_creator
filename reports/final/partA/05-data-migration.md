# 5. Data Migration

The legacy corpus was migrated into the new engine schema on 2026-09-11 by
`python3 -m engine.migrate_legacy --db data/radar.db`, executed against a byte-copy of the
production mirror. The migration is additive by construction — it adds 17 tables and 5 guarded
columns and never renames or drops anything in the 14 pre-existing tables — and every step below
is independently verified against `reports/migration-validation.json` and `data/migration_log.md`,
both regenerated by the same run.

## Steps a–h and results

| Step | What it does | Result |
|---|---|---|
| a — schema | Applies migrations 1 and 2 | 18 tables created (17 new + `schema_migrations` ledger), 5 guarded columns added |
| b — `transcript_meta` | Writes ASR provenance for every `transcripts` row | 273 rows with local faster-whisper provenance; recomputed word count matched `transcripts.words` on all 273 |
| c — frames on disk | Checks every `frames.path` against the filesystem, computes sha256 | 2,653 rows checked: 2,645 present, **8 broken**, all one code (`DcxV37-CJOC`) |
| d — `deepdives.evidence_state` | Tags every deep dive with its sampling method | `fixed9-v1` on all 282 rows — legacy frames are fixed samples, not detected scenes |
| e — August 2026 archive | Imports the pre-database niche-research pass | 8 transcripts and 74 frames over 8 codes imported, 0 base64 fallbacks needed, **6 codes UNRESOLVED** |
| f — `video_state` | Computes the processing-state row for every code | 3,211 rows, one per distinct code in `reels` |
| g — `providers` | Writes provider state from environment presence only | 9 rows; no credential value read or stored |
| h — validation | `PRAGMA integrity_check` + orphan/duplicate checks | `ok`, 0 foreign-key violations, 0 orphaned scores/cards/metrics/topics, 0 PK duplicates |

## Unresolved records

Six codes from the August archive carry a transcript and/or frames but have **no row in `reels`**
— the pass predates the database and their metadata was never re-collected:
`DT0fJmxjVnI, DU9OIJUCBQz, DZw4aTtzJpg, Db9AEm5upfu, DbOUP9OPDAQ, DcdbJKmxZ5o`. Their media analysis
is kept; **no `reels` row was fabricated** for any of them. They have no author, no metrics and no
`video_state` row, and are excluded from every denominator in this report until a paid HikerAPI
lookup resolves them. Two sibling codes from the same archive pass (`DRXZJeHiAES`, `Db5sXEAP6C4`)
*do* have a `reels` row, which is why the corpus tiers below (268, not the spec's illustrative 266)
differ deliberately from earlier documentation.

## August archive import, in detail

`dataset/2026-08-niche-research/` held the first niche pass, made before the database existed and
never previously migrated: 8 transcripts (`{lang, segments}` shape) and 74 jpgs across 8 codes.
The source filenames encode deciseconds, not frame indices (`<code>_0004.jpg` = 0.4s), recovered
and verified against the archive's own `reels_pool.json` durations — e.g. `DU9OIJUCBQz` at
126.47s duration produces frames at 15.8/31.6/47.4/63.2/79.1/94.9/110.7s, exactly `126.47·k/8`.
`frames_b64.json` (7 codes × 6 frames) was not needed — every frame it holds already exists as a
jpg on disk. This closes the one genuine data-recovery gap the audit identified; nothing else in
the three source locations (main's server, Max's branches, the August archive) held unmigrated
signal.

## Damage carried forward, unchanged

`check.py` reports the same single discrepancy before and after migration — 14 of 15 checks pass.
The failure is the same 8 frames on `DcxV37-CJOC` (`frames.exists_ok = 0`): a truncated download
left one of nine frames on disk. The migration makes this **visible in the data** rather than only
in an audit — `frames_state = PARTIAL`, `media_state = MISSING`, flags `BROKEN_FRAME_REFERENCE`
and `MISSING_MEDIA` all set — but does not and cannot repair it, since the source video and the
signed CDN URL that could regenerate it are both gone (chapter 7).

## Re-runnability, proven

The migration was executed twice against a byte-copy of the production database. The second run
produced **identical** `video_state`, `transcript_meta`, `frames`, `transcripts`,
`deepdives.evidence_state` and `providers` rows — every write is `INSERT OR REPLACE` or `UPDATE`
on a deterministic key, the August import only touches codes absent from the target tables, and
step (b) never overwrites a transcript whose provenance a prior step already recorded. Only
`updated_at`, `providers.checked_at` and the log file's own timestamp move between runs. This is
verified behaviour, not a design claim: the two runs' row counts and content were diffed directly.
